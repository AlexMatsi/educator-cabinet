# Правила проєкту

- Пріоритет мають поточне завдання користувача та його узгоджені уточнення.
- Прочитай README.md і документ поточного етапу. Звертайся до docs/PRODUCT.md для правил предметної області. Не перечитуй усю історію без потреби.
- Інтерфейс, доступні користувачу повідомлення та звіти — українською. Код та ідентифікатори можуть бути англійською.
- Основа — Flutter. iPhone є першою цільовою платформою; спільні моделі та правила мають підтримувати подальші Android, web і desktop.
- Завершуй поточний невеликий етап. Не реалізовуй увесь перелік майбутніх функцій одним завданням.
- Пиши простий модульний код. Відокремлюй моделі, правила, доступ до даних і відображення. Не будуй порожню складну інфраструктуру наперед.
- Для розробки використовуй лише синтетичні дані. Не додавай справжні картки, документи, телефони, бази, резервні копії, ключі чи сертифікати.
- Основні функції застосунку плануються без серверної бази та API ШІ. Вебпідтримка не означає синхронізацію або однакові гарантії зберігання на всіх платформах.
- Не запускай додаткових агентів автоматично. Якщо поточне завдання прямо передбачає делегування, використовуй його для конкретної незалежної роботи.
- Використовуй точкові зміни та короткі журнали виконання. Зберігай робочий прогрес у git.
- Перевіряй результат інструментами, що відповідають етапу. Для Flutter: форматування, flutter analyze, змістовні flutter test і доступна збірка.
- Не повідомляй про перевірку на iPhone, iOS Simulator або іншій платформі без фактичного запуску там. У Linux не можна підтвердити iOS-збірку через Xcode.
- Якщо SDK або мережа недоступні, вкажи точну перешкоду і виконані перевірки. Не приховуй помилки та не витрачай багато спроб на ту саму причину.
- Оновлюй README після етапу: що готово, як запустити, що перевірено, що далі.
- Публікацію застосунку та платні сервіси виконуй лише в межах відповідного завдання користувача.
